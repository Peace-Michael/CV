Healthcare Blockchain System – Python & Solidity

Building a Python blockchain and Solidity smart contract for patient record management with role-based access control, tamper-proof audit trails, and deployment to Sepolia testnet.

Introduction

Healthcare practitioners continue to struggle with disjointed patient records across the globe (Hölbl et al., 2018). Blockchain technology presents an evidence-based architectural response to this problem. Its distributed ledger is transparent, programmable and shows evidence of tampering at any given time (Ateniese, 2017).

This report presents a solution built for HealthCare Innovations Ltd structured around blockchain fundamentals. The solution provides two deliverables: a Python-based blockchain and a Solidity smart contract. The latter was deployed to Sepolia Ethereum testnets, enforcing role-based access control over patient record transactions as well as providing unchangeable audit trails verifiable by anyone with network access.

2. Python Blockchain Implementation

2.1 Overview and Design

The implementation builds directly from the simple coin architecture. The healthcare blockchain follows the same structure and is adapted for patient record transactions rather than coin transfers. Patient record specific transaction types, an audit query function, and a longest chain consensus method were added. SHA-256 was the hashing algorithm of choice, available in Python's standard library through hashlib.

Design ComponentDecision and Reason
Block structureindex, timestamp, records list, previous_hash, nonce, hash records
HashingSHA-256 (hashlib)
Proof-of-WorkNonce incremented until hash starts with difficulty leading zeros
ConsensusLongest valid chain rule; replace_chain() adopts a peer chain only if longer and valid
Genesis blockBlock #0 hard-coded with previous_hash='0'; establishes root of trust
Tamper evidenceis_chain_valid() re-calculates every hash and checks chain linkage

2.2 Block Structure and Hashing

Each block contains six features. The hash is computed by serializing all other fields into a single string which was passed through SHA-256. Patient record transactions consist of seven fields: record_id, patient_name, action (ADD / TRANSFER / UPDATE), from_provider, to_provider, details, and a UTC timestamp (Ateniese, 2017).

2.3 Proof-of-Work Mining

The mine_pending_records() method wraps pending transactions into a new block, incrementing nonce until the block hash begins with the required number of zero characters. At difficulty=4, the target is '0000'. In the demonstration run, Block 1 required 51,623 nonce increments and Block 3 required 113,747. An attacker wishing to rewrite Block 1 would require large computational demands, almost infeasible at scale (Antonopoulos, 2017).

2.4 Consensus Mechanism

The replace_chain() method implements the Nakamoto longest valid chain rule. Local nodes only accept an incoming chain that is longer and passes full validation. This single rule is applied consistently by all honest nodes and ensures the network converges on one shared history (Nakamoto, 2008).

3. Smart Contract Implementation (Solidity)

3.1 Rationale for an On-Chain Contract

Decentralized public blockchain provides guarantees that no single party can tamper with or delete records. Healthcare record systems are heavily dependent on that guarantee—a requirement Ethereum smart contracts meet. Once deployed, the state of a smart contract is publicly verifiable, as every function call is recorded as a transaction on the chain (Buterin, 2014).

3.2 Contract Architecture

The PatientRecordContract was written in Solidity version 0.8.20. The contract begins with a PatientRecord struct, establishing the data model for identifying and storing unique inputs. Storage is facilitated through a mapping from uint256 identifier to PatientRecord struct. A totalRecords counter with auto-increment generates sequential record identifiers.

ElementPurpose
totalRecords (uint256)Auto-incrementing counter used as the primary key
owner (address)Set to msg.sender at deployment; only the owner can authorise new providers
authorisedProviders (mapping)mapping(address -bool); only authorised addresses may write records
records (mapping)mapping(uint256 -PatientRecord); private; access through getRecord()
PatientRecord (struct)recordId, patientName, diagnosis, custodian (address), exists (bool), createdAt, updatedAt
onlyOwner modifierReverts if msg.sender is not owner; protects authoriseProvider()
onlyAuthorised modifierReverts if caller not in authorisedProviders; applied to addRecord() and transferRecord()
recordExists modifierReverts if the exists flag is false; prevents reads on uninitialised mapping slots
EventsProviderAuthorised, RecordAdded, RecordTransferred; enables off-chain listeners

3.3 Key Functions

addRecord (patientName, diagnosis): Authorized healthcare providers create new patient records. The function increments totalRecords, assigns a unique identifier, and sets msg.sender as the initial custodian.

transferRecord(recordId, newCustodian): Transfers ownership between authorized providers. Four conditions must be met: record existence, caller is current custodian, receiving address is authorized, and transfer is not to the caller's own address.

getRecord(recordId): Public view function that returns the full PatientRecord. No gas fee is required as it does not modify state. In a real environment, sensitive details would be encrypted.

3.4 Security Considerations

The contract applies role-based access control using onlyOwner and onlyAuthorised modifiers. This prevents unauthorised users from accessing patient information. The exists boolean flag combined with the recordExists modifier ensures interactions only occur with valid patient records (Ethereum Foundation, 2026b).

4. Testing

4.1 Python Blockchain Tests

Five automated tests were created to check that the Python blockchain worked properly:

  • Chain validation: is_chain_valid() returned True after mining a new block, confirming correct block links and hash values.
  • Tamper detection: After changing a stored patient record, validation returned False, identifying unauthorised changes.
  • Genesis block: Confirmed creation with index 0 and previous hash "0".
  • Patient record retrieval: get_records_for_patient("Alice Johnson") returned at least one matching record.

5. Technical Limitations

Key Limitation: The contract stores patient names and diagnoses directly on-chain in plain text. This was useful for demonstration but is not safe for a real hospital system. Under UK GDPR, health data is special category data requiring higher protection.

In a real healthcare system, the better approach would be to store only an encrypted reference or hash on-chain, while keeping the actual medical information in a secure off-chain database (ICO, 2024).

Conclusion

This project successfully delivered a Python-based blockchain and a Solidity smart contract for patient record management. The solution demonstrates:

  • Role-based access control through onlyOwner and onlyAuthorised modifiers
  • Tamper-proof audit trails via blockchain's immutable nature
  • Transparent verification through Sepolia testnet deployment
  • Secure record transfers between authorised providers

While the current implementation stores data in plain text for demonstration, production deployment would require encryption and off-chain storage to comply with GDPR and NHS Digital guidelines.
