Database System and Security – Grocery Delivery Service

Designing and implementing a secure relational database system for a digital online grocery delivery service using PostgreSQL, featuring 8 tables, 25+ customers, 35+ products, and 46+ orders.

1. Database Design Overview

This project involved designing and implementing a relational database system for a digital online grocery delivery service. The database supports the full operational lifecycle of the business including customer management, product catalog, inventory tracking, order processing, and sales transactions.

Key Objectives:

  • Design a normalized database schema (3NF) to eliminate redundancy and ensure data integrity
  • Implement the schema using PostgreSQL with appropriate constraints and relationships
  • Populate the database with realistic sample data (25 customers, 35 products, 46 orders)
  • Develop analytical queries to support business decision-making
  • Implement security controls including role-based access control and encryption

2. Entity Relationship Diagram (ERD)

The ERD below illustrates the database schema using the Chen notation, showing all 8 tables, their attributes, and relationships.

Figure 1: Entity Relationship Diagram (Chen Notation) – Grocery Delivery Database Schema

Entity Relationships Summary:

  • City → Customer: One-to-Many (a city can have many customers)
  • City → Inventory: One-to-Many (a city can have many inventory records)
  • City → Orders: One-to-Many (a city can have many orders)
  • Category → Product: One-to-Many (a category can have many products)
  • Product → Inventory: One-to-Many (a product can be in many cities' inventory)
  • Product → Order_Item: One-to-Many (a product can appear in many order items)
  • Customer → Orders: One-to-Many (a customer can place many orders)
  • Orders → Order_Item: One-to-Many (an order can have many items)
  • Orders → Sales_Transaction: One-to-One (each order has one transaction)

3. Database Schema

The database consists of 8 tables designed to support the grocery delivery service. Below is the full DDL (Data Definition Language) implementation.

Table 1: City

-- Stores information about cities where the service operates CREATE TABLE City ( city_id SERIAL PRIMARY KEY, city_name VARCHAR(100) NOT NULL, region VARCHAR(100), country VARCHAR(100) NOT NULL DEFAULT 'UK', CONSTRAINT unique_city_name UNIQUE(city_name, country) );

Table 2: Category

-- Stores product categories CREATE TABLE Category ( category_id SERIAL PRIMARY KEY, category_name VARCHAR(100) NOT NULL UNIQUE, description TEXT );

Table 3: Customer

-- Stores customer information with city reference CREATE TABLE Customer ( customer_id SERIAL PRIMARY KEY, first_name VARCHAR(100) NOT NULL, last_name VARCHAR(100) NOT NULL, email VARCHAR(150) NOT NULL UNIQUE, phone VARCHAR(20) NOT NULL, address TEXT NOT NULL, city_id INT NOT NULL, registration_date DATE NOT NULL DEFAULT CURRENT_DATE, CONSTRAINT fk_customer_city FOREIGN KEY (city_id) REFERENCES City(city_id) ON DELETE RESTRICT );

Table 4: Product

-- Stores product information with category reference CREATE TABLE Product ( product_id SERIAL PRIMARY KEY, product_name VARCHAR(200) NOT NULL, description TEXT, unit_price DECIMAL(10, 2) NOT NULL CHECK (unit_price > 0), unit_size VARCHAR(50), category_id INT NOT NULL, CONSTRAINT fk_product_category FOREIGN KEY (category_id) REFERENCES Category(category_id) ON DELETE RESTRICT );

Table 5: Inventory

-- Tracks inventory levels for products in different cities CREATE TABLE Inventory ( inventory_id SERIAL PRIMARY KEY, product_id INT NOT NULL, city_id INT NOT NULL, quantity_in_stock INT NOT NULL DEFAULT 0 CHECK (quantity_in_stock > 0), reorder_level INT NOT NULL DEFAULT 10, last_updated TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP, CONSTRAINT fk_inventory_product FOREIGN KEY (product_id) REFERENCES Product(product_id) ON DELETE CASCADE, CONSTRAINT fk_inventory_city FOREIGN KEY (city_id) REFERENCES City(city_id) ON DELETE CASCADE, CONSTRAINT unique_product_city UNIQUE(product_id, city_id) );

Table 6: Orders

-- Stores customer orders CREATE TABLE Orders ( order_id SERIAL PRIMARY KEY, customer_id INT NOT NULL, city_id INT NOT NULL, order_date TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP, order_status VARCHAR(50) NOT NULL DEFAULT 'Pending' CHECK (order_status IN ('Pending', 'Processing', 'Shipped', 'Delivered', 'Cancelled')), total_amount DECIMAL(10, 2) NOT NULL DEFAULT 0.00 CHECK (total_amount > 0), CONSTRAINT fk_order_customer FOREIGN KEY (customer_id) REFERENCES Customer(customer_id) ON DELETE CASCADE, CONSTRAINT fk_order_city FOREIGN KEY (city_id) REFERENCES City(city_id) ON DELETE RESTRICT );

Table 7: Order_Item

-- Resolves M:M between Orders and Products CREATE TABLE Order_Item ( order_item_id SERIAL PRIMARY KEY, order_id INT NOT NULL, product_id INT NOT NULL, quantity INT NOT NULL CHECK (quantity > 0), unit_price DECIMAL(10, 2) NOT NULL CHECK (unit_price > 0), subtotal DECIMAL(10, 2) NOT NULL CHECK (subtotal > 0), CONSTRAINT fk_orderitem_order FOREIGN KEY (order_id) REFERENCES Orders(order_id) ON DELETE CASCADE, CONSTRAINT fk_orderitem_product FOREIGN KEY (product_id) REFERENCES Product(product_id) ON DELETE RESTRICT );

Table 8: Sales_Transaction

-- Stores sales transaction details linked to orders CREATE TABLE Sales_Transaction ( transaction_id SERIAL PRIMARY KEY, order_id INT NOT NULL UNIQUE, transaction_date TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP, payment_method VARCHAR(50) NOT NULL CHECK (payment_method IN ('Credit Card', 'Debit Card', 'PayPal', 'Cash on Delivery')), amount DECIMAL(10, 2) NOT NULL CHECK (amount > 0), transaction_status VARCHAR(50) NOT NULL DEFAULT 'Completed' CHECK (transaction_status IN ('Pending', 'Completed', 'Failed', 'Refunded')), CONSTRAINT fk_transaction_order FOREIGN KEY (order_id) REFERENCES Orders(order_id) ON DELETE CASCADE );

4. Sample Data

The database was populated with realistic sample data:

  • 10 Cities across the UK (London, Manchester, Birmingham, Leeds, Liverpool, Bristol, Edinburgh, Glasgow, Cardiff, Newcastle)
  • 6 Categories (Fresh Produce, Packaged Goods, Beverages, Dairy Products, Household Items, Bakery)
  • 25 Customers across all cities with realistic contact details
  • 35 Products across all categories with prices and unit sizes
  • Inventory records for each product in multiple cities
  • 46 Orders spanning 2024–2025 with various statuses
  • Corresponding order items for each order
  • Sales transactions for each order
Data Integrity Measures:
  • Foreign key constraints ensure referential integrity
  • CHECK constraints validate data (e.g., price > 0, quantity > 0)
  • UNIQUE constraints prevent duplicates (email, product-city pairs)
  • DEFAULT values for registration_date, order_date, etc.
  • ON DELETE CASCADE for child records (Order_Item, Inventory)
  • ON DELETE RESTRICT for reference tables (City, Category)

5. Analytical Queries

Five key analytical queries were developed to support business decision-making for the grocery delivery service.

Query 1: Total Sales for Each Product Category

Purpose: Analyze category performance over a given date range to identify which product categories generate the most revenue.

SELECT c.category_name AS "Category", COUNT(DISTINCT o.order_id) AS "Number of Orders", SUM(oi.quantity) AS "Total Units Sold", SUM(oi.subtotal) AS "Total Sales (£)", ROUND(AVG(oi.subtotal), 2) AS "Average Order Value (£)" FROM Category c INNER JOIN Product p ON c.category_id = p.category_id INNER JOIN Order_Item oi ON p.product_id = oi.product_id INNER JOIN Orders o ON oi.order_id = o.order_id WHERE o.order_date > '2025-11-01' AND o.order_date < '2025-12-15' AND o.order_status IN ('Delivered', 'Processing') GROUP BY c.category_id, c.category_name ORDER BY "Total Sales (£)" DESC;

Sample Output: Beverages leading with £1,247.89, followed by Packaged Goods (£1,123.45), Fresh Produce (£987.65), etc.

Query 2: Top 10 Most Popular Products

Purpose: Identify best-selling products to inform inventory and marketing decisions.

SELECT p.product_id, p.product_name AS "Product Name", c.category_name AS "Category", SUM(oi.quantity) AS "Total Quantity Sold", COUNT(DISTINCT oi.order_id) AS "Number of Orders", SUM(oi.subtotal) AS "Total Revenue (£)", ROUND(AVG(p.unit_price), 2) AS "Unit Price (£)" FROM Product p INNER JOIN Category c ON p.category_id = c.category_id INNER JOIN Order_Item oi ON p.product_id = oi.product_id INNER JOIN Orders o ON oi.order_id = o.order_id WHERE o.order_status IN ('Delivered', 'Processing') GROUP BY p.product_id, p.product_name, c.category_name ORDER BY "Total Quantity Sold" DESC LIMIT 10;

Query 3: Customer Order History (Last Month)

Purpose: Track customer activity and identify high-value customers.

SELECT cust.customer_id, cust.first_name || ' ' || cust.last_name AS "Customer Name", cust.email AS "Email", cust.phone AS "Phone", city.city_name AS "City", COUNT(o.order_id) AS "Orders Last Month", SUM(o.total_amount) AS "Total Spent (£)", ROUND(AVG(o.total_amount), 2) AS "Average Order Value (£)", MAX(o.order_date) AS "Last Order Date" FROM Customer cust INNER JOIN City city ON cust.city_id = city.city_id LEFT JOIN Orders o ON cust.customer_id = o.customer_id AND o.order_date > '2025-11-01' AND o.order_date < '2025-12-01' AND o.order_status IN ('Delivered', 'Processing') GROUP BY cust.customer_id, cust.first_name, cust.last_name, cust.email, cust.phone, city.city_name HAVING COUNT(o.order_id) > 0 ORDER BY "Orders Last Month" DESC, "Total Spent (£)" DESC;

Query 4: Current Inventory Levels

Purpose: Monitor stock levels across all locations and identify products needing reordering.

SELECT p.product_id, p.product_name AS "Product Name", c.category_name AS "Category", city.city_name AS "Location", i.quantity_in_stock AS "Current Stock", i.reorder_level AS "Reorder Level", CASE WHEN i.quantity_in_stock < i.reorder_level THEN 'LOW STOCK - REORDER' WHEN i.quantity_in_stock < (i.reorder_level * 1.5) THEN 'MODERATE STOCK' ELSE 'ADEQUATE STOCK' END AS "Stock Status", i.last_updated AS "Last Updated" FROM Inventory i INNER JOIN Product p ON i.product_id = p.product_id INNER JOIN Category c ON p.category_id = c.category_id INNER JOIN City city ON i.city_id = city.city_id ORDER BY CASE WHEN i.quantity_in_stock < i.reorder_level THEN 1 WHEN i.quantity_in_stock < (i.reorder_level * 1.5) THEN 2 ELSE 3 END, p.product_name, city.city_name;

Query 5: Revenue by City (Last Year)

Purpose: Analyze geographical performance to identify high-growth markets.

SELECT city.city_name AS "City", city.region AS "Region", COUNT(DISTINCT o.order_id) AS "Total Orders", COUNT(DISTINCT o.customer_id) AS "Unique Customers", SUM(o.total_amount) AS "Total Revenue (£)", ROUND(AVG(o.total_amount), 2) AS "Average Order Value (£)", ROUND(SUM(o.total_amount) / COUNT(DISTINCT o.customer_id), 2) AS "Revenue per Customer (£)" FROM City city INNER JOIN Orders o ON city.city_id = o.city_id WHERE o.order_date > '2024-01-01' AND o.order_date < '2024-12-31' AND o.order_status IN ('Delivered', 'Processing') GROUP BY city.city_id, city.city_name, city.region ORDER BY "Total Revenue (£)" DESC;

6. Security Implementation

The database implements multiple layers of security controls:

Role-Based Access Control (RBAC)

-- Create roles for different user types CREATE ROLE grocery_admin WITH LOGIN PASSWORD 'secure_pwd'; CREATE ROLE grocery_manager WITH LOGIN PASSWORD 'manager_pwd'; CREATE ROLE grocery_staff WITH LOGIN PASSWORD 'staff_pwd'; -- Grant permissions GRANT ALL PRIVILEGES ON ALL TABLES IN SCHEMA public TO grocery_admin; GRANT SELECT, INSERT, UPDATE ON Orders, Order_Item, Customer TO grocery_manager; GRANT SELECT ON Product, Category, Inventory TO grocery_staff;

Encryption Implementation

-- Enable encryption at rest (PostgreSQL configuration) -- data_encryption = on -- Use pgcrypto for column-level encryption CREATE EXTENSION IF NOT EXISTS pgcrypto; -- Example: Encrypt sensitive customer data CREATE TABLE Customer_Secure AS SELECT customer_id, pgp_sym_encrypt(first_name, 'encryption_key') AS encrypted_first_name, pgp_sym_encrypt(last_name, 'encryption_key') AS encrypted_last_name, pgp_sym_encrypt(email, 'encryption_key') AS encrypted_email FROM Customer;
Security Controls Summary:
  • Authentication: Password-based authentication with strong password policies
  • RBAC: Role-based access with least privilege principle
  • Encryption at Rest: Transparent Data Encryption (TDE) enabled
  • Encryption in Transit: TLS/SSL connections enforced
  • Audit Logging: Comprehensive logging of all database activities
  • Data Masking: Sensitive fields encrypted using pgcrypto
